# 8. Account Abstraction (ERC-4337): Структура UserOperation и инфраструктура Bundler

Автономные ИИ-агенты не должны управлять нативными блокчейн-кошельками (EOA) с необходимостью вручную рассчитывать газ, следить за балансом ETH/MATIC и подписывать сырые базовые транзакции. В AIFA Network v6.0 мы реализуем стек Account Abstraction на базе стандарта ERC-4337, превращающий каждый кошелек ИИ-агента в программируемый смарт-аккаунт (Smart Contract Wallet).

Это полностью изолирует прикладную логику агента от блокчейн-механики: агент оперирует абстракцией «запрос-оплата» в USDC, а вся работа с комиссиями сети берется на себя специальными узлами-агрегаторами (Bundlers) и контрактом Paymaster.

## 8.1 Анатомия структуры UserOperation

Вместо стандартных Ethereum-транзакций ИИ-агенты формируют псевдо-транзакции — объекты UserOperation (UserOp). Структура упаковывает намерение агента и передается по P2P-сети Bundler-узлов вне основного мемпула блокчейна.

```solidity
struct UserOperation {
    address sender;             // Адрес смарт-аккаунта ИИ-агента
    uint256 nonce;              // Уникальный последовательный номер (Anti-Replay)
    bytes initCode;             // Код создания смарт-аккаунта (если запускается впервые)
    bytes callData;             // Закодированный вызов функции (например, lockFunds в A2AEscrow)
    uint256 callGasLimit;       // Лимит газа на выполнение прикладной логики
    uint256 verificationGasLimit; // Лимит газа на проверку подписей и Paymaster
    uint256 preVerificationGas; // Лимит газа на компенсацию накладных расходов Bundler
    uint256 maxFeePerGas;       // Максимальная цена газа (EIP-1559)
    uint256 maxPriorityFeePerGas;// Чаевые майнеру/валидатору блокчейна
    bytes paymasterAndData;     // Адрес контракта Paymaster + подпись/условия спонсирования
    bytes signature;            // Криптографическая подпись ИИ-агента (secp256k1 / BLS / Passkey)
}
```

Ключевые поля для M2M-взаимодействия:

initCode (Lazy Account Deployment): ИИ-агент создается мгновенно без транзакций в блокчейне. Его смарт-аккаунт генерируется оффчейн детерминированно через CREATE2. Первая транзакция автоматически развертывает контракт-аккаунт благодаря полю initCode.

paymasterAndData: Главный флаг интеграции. Содержит адрес AifaPaymaster.sol и параметры, указывающие, что газ за транзакцию платит не агент, а Paymaster, снимая эквивалент в USDC.

## 8.2 Инфраструктура Bundler: Сборка и упаковка мета-транзакций

Bundler — это специализированный узел инфрастуктуры (может запускаться операторами Супер-Узлов), который слушает отдельный Alt-Mempool для UserOperation.

```
[Агент-Заказчик] ---> (UserOp в USDC) ---> [Alt-Mempool (P2P)]
                                                 │
                                                 ▼
                                        [ Bundler Node ]
                                                 │
                             (Упаковка в bundle: [UserOp1, UserOp2, ...])
                                                 │
                                                 ▼
                                   [ EntryPoint.sol (On-Chain) ]
                                                 │
                                    ┌────────────┴────────────┐
                                    ▼                         ▼
                          [AifaPaymaster.sol]       [A2AEscrow.sol]
                         (Списание USDC за газ)     (Захват эскроу)
```

Пошаговый алгоритм работы Bundler:

Прием и фильтрация (Validation Phase): Bundler получает UserOp через JSON-RPC метод eth_sendUserOperation. Он выполняет оффчейн-симуляцию через контракт EntryPoint.sol, проверяя:
- Валидность подписи UserOp.signature.
- Наличие у AifaPaymaster или агента достаточного баланса/апрува в USDC.
- Отсутствие запрещенных инструкций (например, TIMESTAMP, GASPRICE), которые могут сорвать детерминированность исполнения.

Агрегация (Batching): Bundler объединяет от 10 до 100 валидных UserOp от разных ИИ-агентов в одну стандартную Ethereum-транзакцию.

Отправка в On-Chain EntryPoint: Bundler вызывает функцию handleOps(UserOperation[] ops, address beneficiary) у синглтон-контракта EntryPoint.sol.

Компенсация газа: Bundler платит нативный газ L2-сети (ETH/Base/Arbitrum) из своего кошелька, а контракт EntryPoint мгновенно компенсирует ему затраты из депозита AifaPaymaster.sol + начисляет микро-премию (Bundler Fee).

## 8.3 Контракт EntryPoint.sol: Ядро выполнения

В стандарте ERC-4337 используется единый, проверенный годами и задеплоенный по одинаковым адресам во всех EVM-сетях контракт EntryPoint. Он выступает в роли доверенного оркестратора.

Жизненный цикл вызова handleOps() внутри EntryPoint:

Verification Loop (Цикл проверки):
- Для каждого UserOp проверяется аккаунт sender.
- Если аккаунт еще не создан, исполняется initCode.
- Вызывается функция validateUserOp() на смарт-аккаунте агента для проверки ECDSA-подписи.
- Вызывается validatePaymasterUserOp() на контракте AifaPaymaster.sol для блокировки нужной суммы USDC под покрытие газа.

Execution Loop (Цикл исполнения):
- EntryPoint исполняет callData каждого UserOp (например, отправку вызова в A2AEscrow.sol).
- Измеряется точное количество фактически потраченного газа.
- EntryPoint списывает из депозита Paymaster ровно столько USDC (плюс премия Bundler), сколько потребовалось на gas, и возвращает неиспользованный остаток.

## 8.4 Преимущества для экосистемы AIFA Network

Нулевой фрикцион (Zero Gas Friction): Разработчику ИИ-агента достаточно положить на счет смарт-аккаунта $10$ USDC. Агенту больше никогда не потребуется держать нативный ETH для транзакций.

Сессионные ключи (Session Keys): Смарт-аккаунт агента позволяет ограничить права. Можно выдать временный ключ боту с правом тратить не более $1$ USDC в час и вызывать исключительно контракт A2AEscrow.sol. Если бота взломают, хакер не сможет вывести все средства с аккаунта.

Параллельное исполнение (Atomic Multi-Operations): Агент может в одной UserOp сделать approve(USDC) и lockFunds(), сокращая количество ончейн-шагов и экономию газа на 40%.
